# jannyq

แชทบอทที่เขียนด้วยภาษา Go เชื่อมต่อแพลตฟอร์มแชทกับโมเดลของ **Ollama** หรือ API ที่เข้ากันได้กับ **OpenAI**
พร้อม tool calling สำหรับค้นเว็บและอ่านหน้าเว็บ

> **สถานะ: Phase 3** — Telegram, **web chat** และ terminal, `web_search`, `web_fetch`, ความจำแยกตามแชท,
> `run_command` ใน sandbox แยก, skills และ HTTP server กลางพร้อม **HTTPS ผ่าน Caddy**
> ดู [แผนงาน](#แผนงาน) สำหรับสิ่งที่จะตามมา

## ความสามารถ

- **โมเดล**: Ollama native API (ส่ง `num_ctx` ได้) หรือ endpoint `/chat/completions` ที่เข้ากันได้กับ OpenAI
- **Tools**
  - `web_search` — ค้นผ่าน [SearXNG](https://github.com/searxng/searxng) ที่คุณตั้งไว้
  - `web_fetch` — โหลดหน้าเว็บแล้วแปลงเป็นข้อความอ่านง่าย รองรับ charset เก่าของไทย (เช่น windows-874)
    และอ่านหน้ายาว ๆ ต่อได้ด้วย `offset` กัน SSRF โดยไม่ยอมเชื่อมต่อ IP ภายใน/loopback/link-local
    แม้เป็นปลายทางของ redirect
  - `run_command` — รันคำสั่ง shell ใน sandbox (เปิดให้ทุกคนใช้ได้ แต่มี rate limit, ขีดจำกัดทรัพยากร และ audit log)
    **ปิดเป็นค่าเริ่มต้น**
  - `load_skill` — โหลดคำแนะนำจาก skills ของคุณ
  - `read_attachment`, `search_attachment` — อ่านเอกสารยาว ๆ ที่ผู้ใช้ส่งมาทีละหน้า และค้นข้อความในเอกสาร
    (ดู [รูปภาพ PDF และไฟล์ข้อความ](#รูปภาพ-pdf-และไฟล์ข้อความ))
- **รูปภาพ PDF และไฟล์ข้อความ**: ผู้ใช้ส่งผ่าน Telegram และ web chat ได้ โมเดลหลักดูรูปเอง (จึงต้องเป็นโมเดลที่มี vision)
  ส่วน PDF อ่านใน sandbox และใช้ OCR กับไฟล์สแกน
- **ความจำแยกตามแชท**: ผู้ใช้แต่ละคนและกลุ่มแต่ละกลุ่มมีไฟล์ SQLite ของตัวเอง
  (`<data-dir>/sessions/<channel>/<chat>/session.db`) ลบโฟลเดอร์ของแชทนั้นก็เท่ากับลืมบทสนทนา
- **Compact context**: เมื่อบทสนทนาเกิน `--compact-after` ข้อความ (ค่าเริ่มต้น 200) หรือ prompt ใหญ่เกิน
  `--compact-ratio` ของ `--context-size` ระบบจะให้โมเดลสรุปข้อความเก่าแล้วแทนที่ด้วยสรุป
  ส่วนข้อความล่าสุดคงไว้ตามเดิม
- **หลายภาษา**: ข้อความของระบบมีไทย/อังกฤษ (`--lang`) และสั่งให้โมเดลตอบตามภาษาหลัก
  หรือตามภาษาที่ผู้ใช้พิมพ์ได้ (`--lang-mode follow-user`)
- **ความปลอดภัยพื้นฐาน**: allowlist ผู้ใช้, rate limit ต่อผู้ใช้, คิวต่อแชท, จำกัดจำนวนงานพร้อมกัน,
  จำกัดรอบ tool call และขนาดผลลัพธ์, ไม่แสดง Telegram token ใน log

## เริ่มต้นใช้งาน

### ทดสอบใน terminal (ไม่ใช้ Docker)

```sh
# ต้องมี Ollama ที่รันอยู่และ model ที่รองรับ tool:  ollama pull qwen3:8b
go run ./cmd/jannyq --cli --llm-model qwen3:8b --context-size 16384 --lang th
```

เพิ่ม `--searxng-url http://localhost:8080` เพื่อเปิด `web_search`

### Docker Compose (Telegram + SearXNG + Ollama)

```sh
cp .env.example .env     # ใส่ JANNYQ_TELEGRAM_TOKEN (จาก @BotFather), เลือกโมเดล และ
                         # JANNYQ_SANDBOX_TOKEN (สร้างด้วย: openssl rand -hex 32)
docker compose up -d --build
docker compose logs -f jannyq
```

compose จะเริ่ม jannyq, **sandbox**, SearXNG (เปิดรูปแบบ JSON ไว้แล้วใน `deploy/searxng/settings.yml`), Ollama
และตัวช่วยดาวน์โหลดโมเดล ไม่มีพอร์ตใดถูกเปิดออกภายนอก เพราะ Telegram ใช้ long polling ขาออก
ถ้าใช้ API แบบ OpenAI ภายนอก ให้ตั้งค่าใน `.env` แล้วลบ service ของ Ollama ออก

## การตั้งค่า

ทุกค่าเป็นได้ทั้ง flag และ environment variable: `--llm-model` ⇄ `JANNYQ_LLM_MODEL` โดย flag มีลำดับสูงกว่า
ค่าลับอ่านจากไฟล์ได้ด้วยต่อท้าย `_FILE` เช่น `JANNYQ_TELEGRAM_TOKEN_FILE=/run/secrets/tg`
ใช้ `jannyq --help` ดูรายการทั้งหมด (ตารางค่าหลักอยู่ใน [README.md](README.md#configuration))

### ใครใช้บอทได้บ้าง (`--allowed-users`, `--allowed-groups`)

ค่าเริ่มต้น **ทุกคน** ที่เข้าถึงบอทได้จะคุยได้ (และถ้าเปิด `run_command` ก็สั่งให้บอทรันคำสั่งใน sandbox ได้) ตั้ง `--allowed-users`
(env `JANNYQ_ALLOWED_USERS`) เป็นรายชื่อคั่นด้วยจุลภาคเพื่อให้เฉพาะคนในรายการใช้ได้

**วิธีจับคู่รายการ**

| รายการ | ตรงกับ |
|---|---|
| `123456789` | ผู้ใช้ที่มี ID นี้ใน **ทุก** channel |
| `telegram:123456789` | ID นี้ใน channel นั้นเท่านั้น (`telegram`, `discord`, `line`, `messenger`, `whatsapp`, `cli`) |

- ต้องตรงทุกตัวอักษร แต่ไม่สนตัวพิมพ์เล็ก/ใหญ่ ไม่มี wildcard หรือช่วง ช่องว่างรอบรายการและรายการว่างจะถูกข้าม
- เป็นรายชื่อของ **คน** ไม่ใช่ของแชท: ระบบตรวจทีละคนที่พิมพ์ในกลุ่ม (ถ้าจะอนุญาตทั้งกลุ่ม ดู `--allowed-groups` ด้านล่าง)
- ตรวจก่อน rate limit และก่อนเก็บข้อความหรือเรียกโมเดล ว่าง (ค่าเริ่มต้น) = ทุกคน
- เมื่อใช้หลาย channel ควรเขียน `channel:id` เพราะ ID เปล่า ๆ อาจตรงกับคนละคนบนอีกแพลตฟอร์มที่บังเอิญได้เลขเดียวกัน

**ID ของผู้ใช้ในแต่ละ channel**

| Channel | ID | หาได้จาก |
|---|---|---|
| Telegram | เลข user ID เช่น `123456789` (ไม่ใช่ @username) | ทักบอท `@userinfobot` หรือดูใน log (ด้านล่าง) |
| Discord | snowflake ID เช่น `80351110224678912` | *User Settings → Advanced → Developer Mode* แล้วคลิกขวาที่ผู้ใช้ → *Copy User ID* |
| LINE | user ID ขึ้นต้น `U` (33 ตัวอักษร) | log (ด้านล่าง) เพราะแอป LINE ไม่แสดง |
| Messenger | page-scoped ID (PSID) ของผู้ส่ง | log (ด้านล่าง) |
| WhatsApp | เบอร์โทรรูปแบบสากล **ไม่มี `+`** เช่น `66812345678` | ตัวเบอร์เอง |
| Web chat | ID สุ่มต่อผู้เข้าชม (cookie) | ระบุล่วงหน้าไม่ได้ ดูหมายเหตุด้านล่าง |
| CLI | `local` | – |

**วิธีหา ID ที่ง่ายที่สุด:** เปิดบอท ให้คนนั้นส่งข้อความมา 1 ข้อความ แล้วดู log คนที่ไม่อยู่ในรายการจะทำให้เกิด

```
level=INFO msg="message from user that is not allowed" channel=telegram user=123456789
```

และได้รับคำตอบ *"ขออภัยครับ คุณไม่ได้รับอนุญาตให้ใช้บอทนี้"* (ตามภาษาของบอท) คัดลอก `channel` กับ `user` ไปใส่ในรายการแล้วรีสตาร์ท

**ตัวอย่าง**

```bash
# 1. ใช้คนเดียวบน Telegram (บอทส่วนตัว)
JANNYQ_ALLOWED_USERS=telegram:123456789

# 2. ครอบครัว: 3 คนบน Telegram และ 1 คนบน WhatsApp
JANNYQ_ALLOWED_USERS=telegram:123456789,telegram:987654321,telegram:555000111,whatsapp:66812345678

# 3. คนเดียวกันหลายแพลตฟอร์ม: ใส่ ID ของแต่ละแพลตฟอร์ม (ไม่เหมือนกัน)
JANNYQ_ALLOWED_USERS=telegram:123456789,discord:80351110224678912,line:U4af4980629abcdef0123456789abcdef

# 4. ใช้ channel เดียว ID ไม่กำกวม จึงไม่ต้องใส่คำนำหน้า
JANNYQ_ALLOWED_USERS=123456789,987654321

# 5. ทุกคน (ค่าเริ่มต้น) - ปล่อยว่างหรือไม่ตั้ง
JANNYQ_ALLOWED_USERS=

# 6. แบบ flag
jannyq --allowed-users telegram:123456789,discord:80351110224678912

# 7. ทดสอบใน terminal: ผู้ใช้ CLI คือ "local"
JANNYQ_ALLOWED_USERS=cli:local
```

**กลุ่ม** เฉพาะคนในรายการเท่านั้นที่ได้คำตอบในกลุ่ม (เว้นแต่กลุ่มนั้นอยู่ใน `--allowed-groups` ดูด้านล่าง) ถ้าคนนอกรายการ mention บอท บอทจะตอบว่า "ไม่ได้รับอนุญาต" กับคนนั้น (ไม่ตอบคำถาม
และไม่เก็บข้อความนั้น) ส่วนสิ่งที่คนนอกรายการพูดในกลุ่มโดยไม่เรียกบอท **ก็ไม่ถูกเก็บเช่นกัน** โมเดลจะเห็นบทสนทนา (`--group-context all`)
เฉพาะข้อความของคนในรายการ ถ้าใช้ `--group-reply all` บอทจะตรวจทุกข้อความ สมาชิกนอกรายการจึงได้ข้อความปฏิเสธทุกครั้งที่พิมพ์
ในกลุ่มที่มีคนนอกรายการให้ใช้ `--group-reply mention` (ค่าเริ่มต้น)

**อนุญาตทั้งกลุ่ม (`--allowed-groups`)** การใส่สมาชิกทุกคนของกลุ่มใน `--allowed-users` ลำบากเกินไป `--allowed-groups`
(env `JANNYQ_ALLOWED_GROUPS`) ระบุ **กลุ่ม** แทน: ในกลุ่มที่อยู่ในรายการ บอทจะคุยและตอบ **ทุกคน** ไม่ว่าจะอยู่ใน `--allowed-users` หรือไม่ และเก็บทุกข้อความในกลุ่มเป็นบริบท

- รายการคือ ID ของแชทกลุ่ม เขียนเป็น `id` (ทุก channel) หรือ `channel:id` (เฉพาะ channel นั้น) เทียบตรงตัวแต่ไม่สนตัวพิมพ์ เหมือนรายชื่อผู้ใช้
- สองรายการ **รวมกัน**: ข้อความได้รับคำตอบถ้าผู้ส่งอยู่ใน `--allowed-users` **หรือ** ส่งในกลุ่มที่อยู่ใน `--allowed-groups`
  ผู้ใช้ในรายการยังได้รับคำตอบทุกที่ (แชทส่วนตัวและกลุ่มอื่น) ส่วนกลุ่มอื่นยังตัดสินด้วย `--allowed-users` เหมือนเดิม
- รายการกลุ่ม **ไม่เปิดแชทส่วนตัว**: คนที่อยู่แค่ในกลุ่มที่อนุญาตทักบอทส่วนตัวไม่ได้
- ถ้าตั้ง `--allowed-groups` และปล่อย `--allowed-users` ว่าง บอทจะตอบ **เฉพาะในกลุ่มที่อยู่ในรายการ** (แชทส่วนตัวถูกปฏิเสธ) ตอบทุกคนก็ต่อเมื่อ **ทั้งสองรายการว่าง**
- ใช้กับกลุ่มเท่านั้น (กลุ่มและ supergroup ของ Telegram, ช่องข้อความของ Discord, กลุ่มและ room ของ LINE) Messenger, WhatsApp และ web chat ไม่มีกลุ่ม
- กติกาของกลุ่มยังใช้ต่อ: `--group-reply mention` (ค่าเริ่มต้น) บอทตอบเมื่อถูก mention หรือ reply เท่านั้น ส่วน `--group-reply all` บอทตอบทุกข้อความในกลุ่มที่อนุญาต และไม่มีใครได้ข้อความปฏิเสธ

| Channel | ID กลุ่ม | หาได้จาก |
|---|---|---|
| Telegram | เลขติดลบ เช่น `-1001234567890` (supergroup ขึ้นต้น `-100`) | เพิ่มบอทเข้ากลุ่ม แล้ว @mention บอทจากบัญชีที่ยังไม่อยู่ในรายการ log จะแสดง `chat=…` หรือใช้ `@RawDataBot` |
| Discord | ID ของ **ช่อง** (แต่ละช่องข้อความเป็นแชทของตัวเอง) เช่น `1098765432109876543` | *Developer Mode* คลิกขวาที่ช่อง → *Copy Channel ID* หรือดู log |
| LINE | ID กลุ่ม `C…` (room: `R…`) | log (ด้านล่าง) |

วิธีหา ID กลุ่มที่ง่ายที่สุดเหมือนของผู้ใช้: mention บอทในกลุ่มก่อนใส่ในรายการ บรรทัด log ตอนนี้มีข้อมูลแชทด้วย

```
level=INFO msg="message from user that is not allowed" channel=telegram user=123456789 chat=-1001234567890 group=true
```

```bash
# 8. ทุกคนในกลุ่ม Telegram กลุ่มเดียวใช้ได้ คนอื่นใช้ไม่ได้ (แชทส่วนตัวถูกปฏิเสธ)
JANNYQ_ALLOWED_GROUPS=telegram:-1001234567890

# 9. คุณ (ทุกที่) กับทุกคนในกลุ่มครอบครัว
JANNYQ_ALLOWED_USERS=telegram:123456789
JANNYQ_ALLOWED_GROUPS=telegram:-1001234567890

# 10. ทีม: Telegram 2 กลุ่มกับ Discord 1 ช่อง และแอดมิน 2 คนที่ใช้แบบส่วนตัวได้ด้วย
JANNYQ_ALLOWED_USERS=telegram:123456789,discord:80351110224678912
JANNYQ_ALLOWED_GROUPS=telegram:-1001234567890,telegram:-1009876543210,discord:1098765432109876543

# 11. แบบ flag
jannyq --allowed-users telegram:123456789 --allowed-groups telegram:-1001234567890
```

แค่อยู่ในกลุ่มที่อนุญาตก็พอ ดังนั้น **ใครเข้ากลุ่มนั้นได้ก็ใช้บอทได้** (และถ้าเปิด `run_command` ก็รันคำสั่งใน sandbox ได้) ควรทำกลุ่มให้เป็นส่วนตัวหรือเชิญเข้าเท่านั้น

**ควรรู้เพิ่ม**

- **web chat ใช้คู่กับรายการเหล่านี้ไม่ได้:** ผู้เข้าชมเว็บได้ ID สุ่มและไม่อยู่ในกลุ่มใด จึงไม่มีรายการไหนระบุได้ ทันทีที่รายการใดรายการหนึ่งไม่ว่าง ผู้เข้าชมเว็บทุกคนจะถูกปฏิเสธ
  ถ้าจะจำกัด web chat ให้ใช้ `--web-access-code` แทน (ใครรู้รหัสก็คุยได้) หรือไม่เปิด web channel
- **channel แบบ webhook (LINE, Messenger, WhatsApp) ยังรับข้อความอยู่:** บอทตอบปฏิเสธกลับไป แต่รับ webhook ที่ลงลายเซ็นถูกต้องตามปกติ
  รายการควบคุมว่าใครได้รับบริการ ไม่ได้ควบคุมว่าใครเข้า URL ได้
- **แก้รายการแล้วต้องรีสตาร์ท** (อ่านตอนเริ่มโปรแกรม)
- **ไม่ใช่ระบบล็อกอิน:** ID คือสิ่งที่แพลตฟอร์มรายงาน ความปลอดภัยเท่ากับบัญชีบนแพลตฟอร์มนั้น ถ้าข้อมูลสำคัญควรพิจารณา `--run-command=off`
  และเนื้อหาใน `--knowledge-dir` ด้วย เพราะทุกคนในรายการถามบอทเรื่องฐานความรู้ร่วมได้
- **ใช้ร่วมกับ:** `--rate-limit` (ต่อผู้ใช้ที่ได้รับอนุญาตต่อนาที), `--web-access-code` สำหรับ web chat และเก็บ token ของบอทเป็นความลับ
  (บอท Telegram/Discord ใครก็ค้นเจอ จึงควรมีรายการนี้)

### ข้อควรรู้เกี่ยวกับ Telegram

- ในกลุ่ม บอทจะตอบเมื่อถูก **@mention**, มีคน **reply ข้อความของบอท** หรือเมื่อมี `/command`
- คำสั่ง: `/help`, `/reset` (ลืมบทสนทนา), `/compact` (สรุปข้อความเก่าทันที) ถ้าไม่ต้องการคำสั่งเลย ให้เริ่มบอทด้วย
  `JANNYQ_COMMANDS=false` — ผู้ใช้จะล้างแชทเองไม่ได้ (ผู้ดูแลล้างผ่าน retention หรือลบโฟลเดอร์) ส่วนการ compact อัตโนมัติยังทำงานตามปกติ
- ครั้งแรกที่บอทตอบในแชทหนึ่ง ๆ **โมเดลจะเขียนข้อความแนะนำตัวเอง** (อ่าน system prompt จึงบอกได้ตรงกับ tool/skill ที่ตั้งไว้ และเขียนด้วยภาษา `--lang`) ข้อความนี้ถูกบันทึกในประวัติเหมือนคำตอบปกติ ใช้โมเดลเพิ่ม 1 ครั้งต่อแชท ไม่แนะนำซ้ำแม้ใช้ `/reset` ปิดได้ด้วย `JANNYQ_INTRO=false` ถ้าข้อความแรกคือ `/start` ของ Telegram และปิดคำสั่งไว้ (`JANNYQ_COMMANDS=false`) จะได้ข้อความแนะนำอย่างเดียว ไม่ตอบซ้ำ ส่วนข้อความแรกอื่น ๆ จะได้ข้อความแนะนำแล้วตามด้วยคำตอบ
- ตอนนี้ตอบเป็นข้อความธรรมดา (ยังไม่แสดงผล Markdown)

### Discord

1. สร้าง application ที่ <https://discord.com/developers/applications> เพิ่ม **Bot** แล้วนำ token ใส่ `JANNYQ_DISCORD_TOKEN`
2. ที่ *Bot → Privileged Gateway Intents* เปิด **MESSAGE CONTENT INTENT** ถ้าไม่เปิด Discord จะซ่อนข้อความที่ไม่ได้ mention บอท
   บอทจะไม่ยอมเริ่มทำงานและบอกเหตุผลชัดเจน
3. เชิญบอทด้วย scope `bot` และสิทธิ์ *View Channels*, *Send Messages*, *Read Message History*
- **ไม่ต้องมี URL สาธารณะ**: บอทเปิดการเชื่อมต่อ gateway เอง (ต่อใหม่และ resume เมื่อหลุด)
- ในเซิร์ฟเวอร์บอทตอบเมื่อถูก **@mention** หรือมีคน **reply ข้อความของบอท** ข้อความอื่นเก็บเป็นบริบท (`--group-context all` พร้อมชื่อผู้พูด) แต่ไม่ตอบ
  ในข้อความส่วนตัวตอบทุกข้อความ
- คำสั่ง: Discord เก็บ `/…` ไว้ให้ slash command จึงพิมพ์ **`!reset`**, `!help`, `!compact` (หรือ mention บอทแล้วพิมพ์ `@bot /reset`)
- รูป PDF และไฟล์ข้อความที่แนบมาอ่านได้เหมือน Telegram และคำตอบของบอทไม่เคย ping ใคร (`allowed_mentions` ว่าง)

### LINE

1. ใน [LINE Developers console](https://developers.line.biz/) สร้างช่อง **Messaging API** แล้วนำ *channel secret* และ *channel access token*
   ใส่ `JANNYQ_LINE_CHANNEL_SECRET` และ `JANNYQ_LINE_CHANNEL_TOKEN`
2. LINE เป็นฝ่ายเรียกบอท จึงต้องมี **URL สาธารณะแบบ HTTPS**: ใช้ `docker-compose.public.yml` แล้วตั้ง *Webhook URL* เป็น
   `https://<JANNYQ_DOMAIN>/webhook/line` (`--line-webhook-path`) เปิด *Use webhook* และใน *LINE Official Account Manager* ปิด
   *ข้อความตอบกลับอัตโนมัติ* และ *ข้อความทักทาย* และอนุญาตให้บอทเข้ากลุ่มถ้าต้องการ
- ทุก request ถูกตรวจกับ channel secret (HMAC-SHA256 แบบ constant time) ก่อนอ่านเนื้อหา event ที่ส่งซ้ำถูกข้าม webhook ตอบทันทีแล้วให้โมเดลทำงานทีหลัง
  (เพราะ LINE รอไม่นาน) และ address ที่ส่ง signature ผิดซ้ำ ๆ จะถูกปฏิเสธ
- ใน **กลุ่มและห้อง** บอทตอบเมื่อถูก **@mention** (ตัด mention ออกจากข้อความ) ข้อความอื่นเก็บเป็นบริบท ในแชทส่วนตัวตอบทุกข้อความ
  คนในกลุ่มที่ไม่ได้อนุญาตให้ใช้โปรไฟล์จะแสดงเป็น `user`
- **คำตอบแรกใช้ reply token ของข้อความ (ฟรี)** คำตอบถัดไปหรือคำตอบที่ช้าเกินราว 50 วินาทีจะใช้ **push** ซึ่งนับเข้าโควตาข้อความรายเดือนของบัญชี LINE
  คำตอบยาวถูกแบ่งเป็นหลายข้อความ
- รูปและไฟล์อ่านได้เหมือน Telegram (วิดีโอ เสียง สติกเกอร์ และตำแหน่งไม่รองรับ) ระหว่างที่โมเดลทำงานจะแสดง loading animation ของ LINE ในแชทส่วนตัว

### Messenger และ WhatsApp

ทั้งสองใช้ Graph API ของ Meta และ Meta เป็นฝ่ายเรียก webhook ของบอท จึงต้องมี **URL สาธารณะแบบ HTTPS** (`docker-compose.public.yml`) และ `--listen`
สร้างแอปที่ <https://developers.facebook.com/apps> แล้ว:

- **Messenger** (Facebook Page): เพิ่มผลิตภัณฑ์ *Messenger* สร้าง **Page access token** (`JANNYQ_MESSENGER_PAGE_TOKEN`) คัดลอก **app secret**
  (*App settings → Basic*, `JANNYQ_MESSENGER_APP_SECRET`) คิด **verify token** เอง (`JANNYQ_MESSENGER_VERIFY_TOKEN`) แล้วตั้ง webhook เป็น
  `https://<host>/webhook/messenger` และ subscribe field `messages` ของเพจ
- **WhatsApp** (Cloud API): เพิ่มผลิตภัณฑ์ *WhatsApp* สร้าง **access token** ถาวรของ system user (`JANNYQ_WHATSAPP_TOKEN`) คัดลอก
  **phone number ID** ของเบอร์ธุรกิจ (`JANNYQ_WHATSAPP_PHONE_NUMBER_ID` ไม่ใช่เบอร์โทรศัพท์) **app secret** และ verify token ที่คิดเอง
  แล้วตั้ง webhook เป็น `https://<host>/webhook/whatsapp` และ subscribe field `messages`
- Meta ตรวจ URL ด้วย handshake (บอทตอบด้วย verify token) แล้วเซ็นทุก request ด้วย app secret (`X-Hub-Signature-256`, HMAC-SHA256)
  request ที่ไม่มี/เซ็นผิดถูกปฏิเสธก่อนอ่านเนื้อหา event ที่ส่งซ้ำถูกข้าม และ webhook ตอบทันทีแล้วให้โมเดลทำงานทีหลัง
- ทั้งสองเป็น **แชทตัวต่อตัว** ตอบทุกข้อความ (กล่องข้อความของ Page และ WhatsApp Cloud API ไม่มีกลุ่ม) ชื่อผู้ใช้มาจาก Graph API เมื่อแอปมีสิทธิ์
  (Messenger ต้องขออนุญาต; WhatsApp ส่งชื่อโปรไฟล์มาให้) ไม่เช่นนั้นเรียกว่า `user`
- รูป PDF และไฟล์ข้อความอ่านได้เหมือน Telegram token จะถูกส่งให้ Meta เท่านั้น ไม่ส่งไปยังลิงก์ไฟล์ของ Messenger วิดีโอ เสียง สติกเกอร์ ตำแหน่ง และ contacts ไม่รองรับ
- **กฎ 24 ชั่วโมงของ Meta**: ตอบได้ภายใน 24 ชั่วโมงหลังข้อความล่าสุดของผู้ใช้ คำตอบที่ช้ากว่านั้น Meta จะปฏิเสธ (บันทึกใน log)
  WhatsApp ยังต้องให้แอปอยู่ในโหมด *live* และสำหรับเบอร์อื่นนอกจากเบอร์ทดสอบต้องยืนยันตัวตนธุรกิจ
- คำตอบยาวถูกแบ่ง (Messenger 2,000 ตัวอักษร WhatsApp 4,096) ระหว่างที่โมเดลทำงาน Messenger แสดงสัญลักษณ์กำลังพิมพ์ ส่วน WhatsApp ทำเครื่องหมายว่าอ่านแล้วพร้อม typing indicator

### การเลือกโมเดล

โมเดลต้องรองรับ **tool calling** ถึงจะใช้ `web_search`/`web_fetch` ได้ (Ollama: qwen3, llama3.1 ขึ้นไป ฯลฯ)
ถ้าโมเดลปฏิเสธ tools ระบบจะบันทึกคำเตือนและคุยต่อโดยไม่ใช้ tools
และควรตั้ง `--context-size` เสมอเมื่อใช้ Ollama เพราะค่าเริ่มต้นของ Ollama เล็กมาก

## บริบทของบทสนทนา: เวลาและชื่อ

ทุกข้อความของผู้ใช้ถูกส่งให้โมเดลพร้อม header:

```
[1997-07-16T19:20:44+01:00] Ann#7f3a: เจอกันเที่ยงไหม?     ← กลุ่ม
[1997-07-16T19:21:02+01:00] ช่วยแปลให้หน่อย                    ← แชทส่วนตัว
```

- **เวลา** เป็น ISO 8601 พร้อม offset ของเขตเวลาตอนนั้น (`--timezone`) ใช้เวลาจากแพลตฟอร์มเมื่อมี (Telegram มี)
  และเก็บไปกับข้อความ system prompt ไม่มีนาฬิกา: header ของข้อความล่าสุดคือเวลาปัจจุบัน ทำให้ส่วนต้นของบทสนทนา
  เหมือนเดิมทุกข้อความ Ollama/OpenAI จึงใช้ cache เดิมได้แทนที่จะอ่านประวัติทั้งหมดใหม่ทุกครั้ง
- **ชื่อ**: ในกลุ่ม header ระบุผู้พูด `#7f3a` คือแท็กสั้นที่คงที่ต่อคนต่อแชท ใช้แยกคนชื่อซ้ำหรือคนที่เปลี่ยนชื่อ
  ID จริงของแพลตฟอร์มไม่ถูกส่งให้โมเดล ส่วนแชทส่วนตัว system prompt บอกชื่อคู่สนทนาครั้งเดียว
- **เก็บทุกข้อความในกลุ่ม** (`--group-context all` ค่าเริ่มต้น) แม้ไม่มีใครเรียกบอท เพื่อให้รู้ว่าใครพูดอะไร
  แต่บอทตอบเฉพาะเมื่อถูก mention, reply หรือสั่งคำสั่ง Telegram ต้องปิด privacy mode
  (BotFather → `/setprivacy` → Disable) จึงจะเห็นข้อความในกลุ่ม ใช้ `--group-context addressed` เพื่อเก็บเฉพาะที่เรียกบอท
- **ลำดับ**: เก็บตามลำดับที่ส่งจริง แม้ข้อความค้างมาเป็นชุดหรือแชทกำลังยุ่ง และถ้ามีข้อความมาคั่นระหว่างรอ
  โมเดลจะถูกบอกว่ากำลังตอบข้อความไหน
- **Compaction** เก็บว่าใครพูดอะไรเมื่อวันไหน และห้องที่ไม่มีใครเรียกบอทก็ถูกสรุปเบื้องหลัง จึงโตไม่จำกัดไม่ได้
- **กันการปลอม**: ชื่อถูกล้าง (ไม่มีอักขระควบคุม/ล่องหน, วงเล็บ, โคลอน, ยาวไม่เกิน 32 ตัวอักษร) และบรรทัดในข้อความที่ดูเหมือน header
  จะกลายเป็นข้อความธรรมดา จึงไม่มีใครแอบอ้างเป็นคนอื่นได้

แชทที่เก็บไว้ก่อนเวอร์ชันนี้ใช้ต่อได้ โดยแสดงเวลาที่ข้อความถูกเขียนลงไป

## รูปภาพ PDF และไฟล์ข้อความ

ส่งรูป ไฟล์ PDF หรือไฟล์ข้อความมา (จะมีคำบรรยายหรือไม่ก็ได้) โมเดลจะอ่านให้:

| ไฟล์ | สิ่งที่โมเดลได้รับ |
|---|---|
| **รูปภาพ** (JPEG, PNG, GIF, WebP) | ตัวรูปให้โมเดลหลักดูเอง ระบบหมุนรูปให้ตั้งตรงตาม EXIF ย่อให้ด้านยาวไม่เกิน `--image-max-edge` (1568 px) วางบนพื้นขาว แล้วเข้ารหัส JPEG ใหม่ ซึ่งตัด metadata (พิกัด GPS, รุ่นกล้อง) ทิ้งด้วย ต้องใช้โมเดลที่มี vision: `--vision=auto` จะถาม Ollama (`/api/show`) ส่วน `--llm-provider=openai` จะถือว่าดูรูปได้ ถ้าโมเดลของคุณดูรูปไม่ได้ให้ใช้ `--vision=off` เมื่อไม่มี vision ระบบจะตอบปฏิเสธรูปภาพอย่างชัดเจน |
| **PDF ที่มีข้อความ** | ข้อความที่สกัดได้แยกทีละหน้า ถ้าไม่เกิน `--attach-inline-chars` (6000 ตัวอักษร) จะแสดงในข้อความเลย ถ้ายาวกว่านั้นโมเดลจะเห็นแค่ขนาดเอกสาร แล้วอ่านทีละหน้าด้วย `read_attachment` หรือค้นด้วย `search_attachment` |
| **PDF สแกน** (ไม่มีข้อความ) | ข้อความที่รู้จำด้วย Tesseract (`--ocr-langs` ค่าเริ่มต้น `eng` และเพิ่ม `tha` เมื่อ `--lang th`) และถ้าโมเดลมี vision จะได้ภาพของ `--vision-pages` (3) หน้าแรกด้วย ถ้าไม่มีทั้ง OCR และ vision จะปฏิเสธไฟล์ |
| **ไฟล์ข้อความ** (txt, md, csv, json, โค้ด …) | ถอดรหัส (UTF-8, UTF-16 หรือ Windows-874 ของไทย) แล้วจัดการเหมือนข้อความของ PDF |

ข้อควรรู้:

- **ชนิดไฟล์ตัดสินจากเนื้อหา** ไม่ใช่ชื่อไฟล์หรือชนิดที่แอปอ้าง ไฟล์อื่น ๆ (zip, exe …) จะถูกปฏิเสธ
- **PDF เป็นข้อมูลที่ไว้ใจไม่ได้และ parser ก็ซับซ้อน** jannyq จึงให้ **sandbox** เป็นผู้อ่าน (`pdfinfo`, `pdftotext`, `pdftoppm`,
  `tesseract` มีใน image ของ sandbox) แทนที่จะแกะไฟล์ในโพรเซสเดียวกับ secret ของบอท เมื่อ `--pdf-engine=auto`
  จะทำเช่นนี้ทุกครั้งที่ตั้ง `--sandbox-url` — **แม้ `--run-command=off`** — และ sandbox มีเครื่องมือครบ
  ไม่เช่นนั้นจะใช้ตัวอ่าน Go ในตัว (ไม่มี OCR ไม่มีภาพหน้า และมี warning ใน log) ส่วน `--pdf-engine=sandbox` จะไม่ถอยไปใช้ตัวในตัว
- ข้อความจากไฟล์คือ **ข้อมูล ไม่ใช่คำสั่ง**: ถูกครอบด้วยเครื่องหมายเริ่ม/จบ ข้อความที่เลียนแบบเครื่องหมายหรือ header ของข้อความ
  ถูกทำให้ใช้ไม่ได้ และ system prompt บอกโมเดลว่าห้ามทำตาม
- **ส่งเฉพาะรูปล่าสุด**: ข้อความที่มีรูป `--image-messages` (3) ข้อความล่าสุดเท่านั้นที่ส่งรูปให้โมเดล ข้อความเก่ากว่านั้นเหลือเป็นโน้ต
  ("ไม่ได้แสดงรูปแล้ว") เพราะรูปกินบริบทมากกว่าคำอธิบายมาก และรูปนับรวมในการตัดสินใจ compact
- ไฟล์ทั้งหมดเก็บในโฟลเดอร์ของแชทนั้น (`<data-dir>/sessions/…/files/`) จำกัด `--attach-chat-mb` (200) ต่อแชท โดยลบไฟล์เก่าสุดก่อน
  และ `/reset` ลบหมด ถ้าเปิด `run_command` จะมีสำเนาใน workspace ของแชทที่ `inbox/<id>-<ชื่อ>` (`--attach-inbox`) ให้คำสั่งใช้งานได้
- **ขีดจำกัด**: `--attach-max-mb` (20) ต่อไฟล์, `--attach-per-message` (5), `--attach-rate` (10 ไฟล์ต่อผู้ใช้ต่อนาที),
  `--pdf-max-pages` (200), `--ocr-max-pages` (15), รูปเกิน 40 ล้านพิกเซลถูกปฏิเสธก่อนถอดรหัส
  ข้อความในกลุ่มที่ไม่ได้เรียกบอทและมีไฟล์ จะบันทึกแค่ว่ามีการส่งไฟล์ ไม่โหลดหรือเปิดอ่าน
- **Telegram**: รูปและเอกสาร (Bot API จำกัด 20 MB) อัลบั้มรูปรวมเป็นข้อความเดียว **Web chat**: ปุ่ม 📎, ลากวาง หรือวาง (paste)
  `--web-max-upload-mb` (10) และ `--web-max-files` (4) ช่องทางอื่นตามมากับ phase ของแต่ละช่องทาง
- ปิดทั้งหมดด้วย `--attachments=false`

## ฐานความรู้ (Knowledge base / RAG)

ตั้ง `--knowledge-dir` ชี้ไปที่โฟลเดอร์ แล้วทุกคนที่คุยกับบอทถามเรื่องเอกสารในนั้นได้ โมเดลจะเรียก `knowledge_search`
(ได้ข้อความตอนที่เกี่ยวข้องพร้อมชื่อไฟล์และหน้า) และ `knowledge_files` (ดูว่ามีเอกสารอะไรบ้าง) แล้วตอบพร้อมอ้างแหล่งที่มา

- **ไฟล์ที่รองรับ**: PDF (รวมไฟล์สแกนด้วย OCR ใน sandbox), `txt md rst csv tsv json jsonl xml yaml toml ini log srt vtt tex`
  อ่านโฟลเดอร์ย่อยด้วย ข้ามไฟล์/โฟลเดอร์ที่ขึ้นต้นด้วยจุด, symbolic link และไฟล์ชนิดอื่น
- **ค้นแบบผสม**: ดัชนี full-text (SQLite FTS5 แบบ trigram จึงค้นภาษาไทย จีน และภาษาที่ไม่เว้นวรรคได้) ร่วมกับ embedding เมื่อตั้ง
  `--embed-model` (Ollama `/api/embed` หรือ `/embeddings` แบบ OpenAI) แล้วรวมอันดับด้วย reciprocal rank fusion และตัดผลที่คล้ายต่ำกว่า
  `--knowledge-min-similarity` ถ้าไม่มี embedding model หรือเข้าถึงไม่ได้ในขณะนั้น จะค้นด้วยคำอย่างเดียวและบอกในคำตอบ
  Ollama แนะนำ `bge-m3` (หลายภาษา รวมไทย) หรือ `nomic-embed-text` (เล็กกว่า) การเปลี่ยน `--embed-model` จะ embed ข้อความที่เก็บไว้ใหม่
  โดยไม่ต้องอ่านไฟล์ซ้ำ
- **รายการหรือหัวข้อที่ยาวข้ามหลาย passage**: เอกสารถูกตัดเป็น passage ประมาณ `--knowledge-chunk-chars` (1200) ตัวอักษร รายการจึงอาจอยู่ครึ่งหนึ่งใน
  passage หนึ่งและอีกครึ่งใน passage ถัดไป (เช่น ผลลัพธ์การเรียนรู้ 9 ข้อของหลักสูตร แล้วโมเดลตอบแค่ 5 ข้อแรก) ผลค้นหาจึงบอกตำแหน่งของแต่ละ passage
  (`passage 44 of 487`) และ **สำหรับ 2 ผลลัพธ์แรก ระบบเพิ่มส่วนที่เหลือของหัวข้อเดียวกันให้อัตโนมัติ**: passage ย้อนไปถึงจุดที่หัวข้อเริ่ม (`[1, before]`) และต่อไปจนถึง
  passage ที่หัวข้อใหม่ระดับเดียวกันหรือสูงกว่าเริ่มขึ้น (`[1, continued]`) ระบบหาหัวข้อจากข้อความ: หัวข้อ Markdown แบบ `#` และหัวข้อที่มีเลขกำกับ เช่น `1.5.3 ผลลัพธ์…`
  หรือ `2.1) …` (อย่างน้อยสองระดับ รายการอย่าง `1.` หรือ `2)` จึงไม่ถูกนับเป็นหัวข้อ) ทำงานจาก passage ที่เก็บไว้แล้ว ดัชนีเดิมใช้ได้โดยไม่ต้องสร้างใหม่
  เพิ่มได้สูงสุด `--knowledge-expand-chars` (3000, `0` = ปิด) ตัวอักษรต่อผลลัพธ์ ข้อความที่ไม่มีหัวข้อจะได้แค่ passage ถัดไป ถ้าหัวข้อยาวกว่านั้น โมเดลมี
  `knowledge_read` อ่านต่อจาก passage ใดก็ได้ และถูกสั่งให้ใช้เมื่อรายการหรือตารางยังถูกตัดค้าง
- **ทำให้โมเดลใช้ฐานความรู้อย่างไร**: system prompt จะแสดงรายการเอกสาร (ชื่อไฟล์และบรรทัดแรก ๆ ของไฟล์เป็นชื่อเรื่อง) และสั่งให้โมเดลเรียก
  `knowledge_search` **ก่อน** สำหรับเรื่องที่เอกสารเหล่านั้นอาจครอบคลุม หรือคำที่ไม่รู้จัก โมเดลที่ถูกบอกแค่ว่า "มีฐานความรู้" มักตอบจากความจำแทน
  บางโมเดลเรียก tool ไม่ได้เลย (log ขึ้น `model does not support tools`) สำหรับโมเดลเหล่านี้ `--knowledge-prefetch auto` (ค่าเริ่มต้น) จะค้นฐานความรู้
  ให้ด้วยข้อความของผู้ใช้แล้วใส่ผลลัพธ์ไว้หน้าโมเดล `always` ทำให้ทุกข้อความแม้โมเดลเรียก tool ได้ (เชื่อถือได้กว่าสำหรับโมเดลเล็ก แต่ค้นทุกข้อความและอาจมีข้อความที่ไม่เกี่ยวข้อง)
  `off` คือไม่ทำเลย ถ้าบอทยังตอบจากความจำ: ใช้โมเดลที่รองรับ tool, ตั้ง `--knowledge-prefetch always` และเพิ่มโมเดล embedding (`--embed-model`)
- **สร้างให้เสร็จก่อนบอทเริ่มทำงาน**: ตอนเริ่มโปรแกรม ระบบตรวจทั้งโฟลเดอร์และสร้าง/ปรับปรุงดัชนีให้เสร็จก่อน (อ่านไฟล์ใหม่และไฟล์ที่แก้ ลืมไฟล์ที่ลบ
  ทำ embedding และรอไฟล์ที่ยังคัดลอกไม่เสร็จ) แล้วจึงเริ่ม channel และเว็บเซิร์ฟเวอร์ log จะแสดง `still building the knowledge base` ทุก 15 วินาที
  โฟลเดอร์ใหญ่ที่ต้อง OCR อาจใช้เวลานาน ถ้าไม่ต้องการรอ ตั้ง `JANNYQ_KNOWLEDGE_STARTUP_SYNC=false` เพื่อให้สร้างเบื้องหลังขณะที่บอทตอบได้จากส่วนที่ทำเสร็จแล้ว
  ถ้าเข้าถึงโมเดล embedding ไม่ได้จะไม่บล็อกการเริ่ม ไฟล์เหล่านั้นค้นด้วยคำไปก่อนจนกว่าการสแกนเบื้องหลังจะทำ embedding ให้ (มีคำเตือนบอกจำนวน)
- **ดัชนีตามโฟลเดอร์**: ทุก `--knowledge-interval` (30 วินาที) ระบบสแกนโฟลเดอร์ ไฟล์ใหม่ถูกอ่าน ไฟล์ที่แก้ถูกอ่านใหม่ ไฟล์ที่ลบถูกลืม
  ไฟล์ที่เปลี่ยนชื่อยังใช้ข้อความเดิม (ดูจาก hash ไม่ต้อง embed ใหม่) ไฟล์ที่แค่ถูก touch ไม่เสียต้นทุน และไฟล์ที่เพิ่งเปลี่ยนจะรอให้นิ่งก่อน
  (ไม่ index ไฟล์ที่ยังคัดลอกไม่เสร็จ) ไฟล์ที่อ่านไม่ได้ (เสียหาย ตั้งรหัสผ่าน ใหญ่เกิน) จะแสดงพร้อมเหตุผลและลองใหม่เมื่อไฟล์เปลี่ยน
  ถ้าโฟลเดอร์หายไปตอนสแกน ดัชนีจะถูกเก็บไว้ ไม่ถูกล้าง
- **เก็บที่ไหน**: `<data-dir>/knowledge.db` (`--knowledge-db`) ไฟล์เดียว ลบทิ้งเพื่อสร้างใหม่ได้ การสแกนครั้งแรกทำเบื้องหลัง
  ระหว่างนั้นคำตอบจะบอกว่าดัชนียังไม่ครบ
- **ใช้ร่วมกันทุกคน** ที่เข้าถึงบอทได้ — ใส่เฉพาะสิ่งที่ทุกคนอ่านได้ และข้อความจากเอกสารถูกส่งให้โมเดลเป็นข้อมูล ไม่ใช่คำสั่ง
- **ขีดจำกัด**: `--knowledge-max-file-mb` (50), `--knowledge-pdf-max-pages` (1000), `--knowledge-ocr-pages` (100; `0` = ปิด OCR ของฐานความรู้)
  embedding ถูกค้นในหน่วยความจำ เหมาะกับไม่เกินหลักแสนตอน (โมเดล 1024 มิติใช้ราว 4 KB ต่อตอน)
- **Docker**: `docker-compose.yml` mount `./knowledge` เป็น `/knowledge` แบบอ่านอย่างเดียว และ `ollama-pull` ดาวน์โหลด
  `JANNYQ_EMBED_MODEL` (`bge-m3` ใน `.env.example`) วางไฟล์ใน `./knowledge` แล้วรอครึ่งนาที

## การดูแลระบบ

คู่มือสำหรับเปิดบอทให้ผู้อื่นใช้อยู่ที่ **[docs/DEPLOYMENT.th.md](docs/DEPLOYMENT.th.md)** (ฉบับเต็มภาษาอังกฤษ [DEPLOYMENT.md](docs/DEPLOYMENT.md)):
เช็กลิสต์ก่อนเปิดสาธารณะ, monitoring, backup และการซ้อมกู้ข้อมูล, การอัปเกรด, การเก็บข้อมูล และตัวอย่าง systemd
เครื่องมือที่เกี่ยวข้อง: **metrics** แบบ Prometheus (`--metrics-listen`, `--metrics-token`), `/healthz` และ `/readyz`,
**backup** (`--backup-dir` และคำสั่ง `jannyq backup`, `jannyq verify`, `jannyq restore --from FILE [--force]`) และ **retention** (`--retention-days`)

**log บน console** (`--log-level info` เป็นค่าเริ่มต้น, `--log-json` สำหรับ JSON) แสดงว่าบอททำอะไรอยู่ แต่ไม่แสดงสิ่งที่ผู้ใช้พิมพ์:

```
level=INFO msg="user connected" channel=telegram user=123456789 name="Ann Lee" chat=123456789 group=false
level=INFO msg="message received" channel=telegram chat=123456789 user=123456789 group=false addressed=true chars=34 files=0
level=INFO msg="tool call" tool=knowledge_search chat=telegram:123456789 user=123456789 duration=41ms bytes=5230
level=INFO msg=reply channel=telegram chat=123456789 user=123456789 result=ok delivered=true chars=412 took=8.2s
```

*user connected* คือข้อความแรกของผู้ใช้คนนั้นนับตั้งแต่เริ่มบอท (web chat: ผู้เข้าชมเปิดหน้าเว็บ แสดงด้วย hash สั้น ๆ แทน ID: `web visitor connected`,
`web chat opened`/`closed`) log ยังแสดงข้อความที่ถูกปฏิเสธ (`message from user that is not allowed`, `message refused: rate limit`, `webhook refused: bad signature`),
คำสั่ง, การแนะนำตัว, tool call, การทำดัชนี, backup, การเริ่ม/หยุด channel และการปิดโปรแกรม โดย **ไม่** บันทึกข้อความ คำตอบ หรืออาร์กิวเมนต์ของ tool
ข้อความในกลุ่มที่เก็บเป็นบริบทอย่างเดียวและทุกคำขอไปยังโมเดล (จำนวน token, เวลา) จะเห็นที่ `--log-level debug`

## Web chat

```sh
jannyq --web --listen :8080 --llm-model qwen3:8b      # แล้วเปิด http://localhost:8080/
```

ผู้เยี่ยมชมแต่ละคนได้คุกกี้ session ที่เซ็นลายเซ็นและเป็น `HttpOnly` พร้อมบทสนทนาส่วนตัวของตัวเอง
หน้าเว็บทั้งหมดมาจากตัวบอทเอง ใต้ Content-Security-Policy ที่เข้มงวด (ไม่มี script ฝังหรือจากภายนอก)
ข้อความตอบกลับสร้างจาก DOM node ไม่ใช่สตริง HTML จึงแสดง HTML ที่แฝงมาเป็นข้อความธรรมดา และทำลิงก์ให้กดได้เฉพาะ `http(s)`

- **ใครใช้ได้**: ทุกคน หรือเฉพาะผู้ที่รู้ `--web-access-code` (จำกัดความถี่ตามที่อยู่ เปลี่ยนรหัสแล้วทุกคนต้องเข้าใหม่)
- **กัน cross-site**: `POST` ต้องเป็น `application/json` และ Origin ตรงกับเว็บ, คุกกี้ `SameSite=Lax`
- **จำกัดต่อที่อยู่ IP**: ข้อความต่อนาที, session ใหม่ต่อชั่วโมง, จำนวน stream, ข้อความที่ประมวลผลพร้อมกัน
  (การสร้าง session ใหม่ **ไม่** รีเซ็ตขีดจำกัดเหล่านี้) และ `run_command` จากเว็บมี quota ที่เข้มกว่า (`--web-run-rate`)
- **ที่อยู่ client จริง**: เชื่อ `X-Forwarded-For` เฉพาะจาก `--trusted-proxies`

ถ้าไม่ตั้งรหัสเข้าใช้ ใครก็ตามที่เข้าถึงได้จะแชทได้ และทุกข้อความใช้เวลาของโมเดล จึงควรตั้งรหัสหรือคง rate limit ให้ต่ำ

## เปิดใช้งานสาธารณะ (HTTPS)

`docker-compose.public.yml` เพิ่ม [Caddy](https://caddyserver.com/) ที่ขอและต่ออายุใบรับรอง Let's Encrypt เอง และเปิด web chat:

```sh
# .env: JANNYQ_DOMAIN=bot.example.com  JANNYQ_WEB_ACCESS_CODE=...   (DNS ชี้มาที่เซิร์ฟเวอร์ เปิดพอร์ต 80/443)
docker compose -f docker-compose.yml -f docker-compose.public.yml up -d --build
```

เปิดออกภายนอกเฉพาะ Caddy ส่วน jannyq อยู่ใน network `edge` ส่วนตัวและเชื่อ header ที่ Caddy ส่งมาเท่านั้น
Telegram/Discord ไม่ต้องมี URL สาธารณะ ส่วน LINE, Messenger และ WhatsApp ต้องมี และจะใช้เซิร์ฟเวอร์เดียวกันนี้

## `run_command` และ sandbox

การให้โมเดลรันคำสั่ง shell ให้ใครก็ตามที่แชทเข้ามาเป็นเรื่องอันตราย (โมเดลถูกหลอกได้ และข้อความจากเว็บก็พยายามสั่งโมเดลได้)
jannyq จึง **ไม่รันคำสั่งเองเด็ดขาด** แต่ส่งไปให้ **sandbox executor** (`jannyq sandbox` คนละ container)
ซึ่งไม่มี secret ใด ๆ และบังคับขีดจำกัดทั้งหมด:

- **container แยก** ไม่มี token/API key/ฐานข้อมูลของบอท อยู่ใน Docker network แบบ internal (ไม่มีอินเทอร์เน็ต)
  มองไม่เห็น Ollama/SearXNG และ environment ของคำสั่งถูกล้างหมด
- **หนึ่งแชทหนึ่ง user**: executor เริ่มเป็น root แต่เหลือเพียง capability ที่จำเป็น แล้วรันแต่ละ workspace
  เป็น uid ที่ไม่มีสิทธิ์ของตัวเอง (โฟลเดอร์ `0700`) แชทจึงอ่าน/แก้/ส่ง signal หากันไม่ได้ และอ่าน environment
  ของ executor (token) ไม่ได้ คำสั่งไม่ใช่ root เด็ดขาด
- **ขีดจำกัดต่อคำสั่ง**: timeout (30 วินาที สูงสุด 120) พร้อมฆ่าทั้ง process group, CPU, จำนวนไฟล์ที่เปิด, ขนาดไฟล์,
  stdin ปิด, ตัด output (เก็บหัวและท้าย)
- **ขีดจำกัดต่อแชท**: quota 256 MB (เกินแล้วเขียนไฟล์ไม่ได้แต่ลบได้), รันทีละคำสั่ง, ลบ workspace ที่ไม่ใช้ 7 วัน
- **ขีดจำกัดรวม**: จำกัดจำนวนงานพร้อมกัน, `pids_limit`, memory/CPU, root filesystem แบบ read-only, `--run-rate` ต่อผู้ใช้
- **ยืนยันตัวตน** ด้วย bearer token (อย่างน้อย 16 ตัวอักษร) และ **audit log** ทุกคำสั่ง
- `/reset` ลบ workspace ของแชทนั้นด้วย

**ข้อจำกัดที่ต้องรู้**: container ไม่ใช่ VM ช่องโหว่ระดับ kernel อาจหลุดออกมาได้ ถ้าเปิดสาธารณะควรใช้ gVisor
(`runtime: runsc`) หรือเครื่องแยก การเปิดอินเทอร์เน็ตให้คำสั่ง (`docker-compose.egress.yml`) ทำให้ผู้ใช้ส่ง request
ออกจาก IP ของเซิร์ฟเวอร์คุณได้ ต้องอ่านคำเตือนในไฟล์นั้นและบล็อกช่วง IP ภายในก่อน ส่วนโหมด `host`
มีไว้ทดลองส่วนตัวเท่านั้น และควรรู้ว่าทุกแชทใช้ kernel และงบ CPU/หน่วยความจำร่วมกัน, command line ของ process
คนอื่นมองเห็นได้ผ่าน `/proc` (อย่าพิมพ์ secret ในคำสั่ง), และพื้นที่ดิสก์โตตามจำนวนแชท จึงควรให้ `/work`
อยู่บน volume ที่จำกัดขนาด

## Skills

skill คือโฟลเดอร์ที่มี `SKILL.md`: คำอธิบายสั้น ๆ ใน YAML front matter ตามด้วยคำแนะนำ โมเดลจะเห็นแค่ชื่อและคำอธิบาย
แล้วเรียก `load_skill` อ่านรายละเอียดเมื่อคำขอตรงกัน โฟลเดอร์ถูก mount แบบ read-only เข้า sandbox ด้วย
skill จึงมีสคริปต์ให้รันได้ และระบบสแกนโฟลเดอร์ใหม่ทุกไม่กี่วินาทีโดยไม่ต้อง restart
ดูตัวอย่างใน [`skills/`](skills/)
